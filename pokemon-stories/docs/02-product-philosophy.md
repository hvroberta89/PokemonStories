# Product Philosophy

## Purpose

This document defines the product philosophy behind Pokémon Stories.

Unlike the Product Vision, which explains what we are building, this document explains how product decisions should be made.

Whenever multiple valid solutions exist, these principles should guide the decision.

Features that align with these principles strengthen the product.

Features that contradict them should be reconsidered.

---

# Our Mission

Pokémon Stories exists to help Game Masters tell better stories.

The application should make storytelling easier, faster and more enjoyable without taking creative control away from the Game Master.

Technology exists to support imagination.

Never to replace it.

---

# Core Beliefs

## Stories Matter More Than Data

Users do not create databases.

They create memories.

The application should present stories, characters and adventures—not records, forms and entities.

Whenever a choice exists between exposing technical information or reinforcing the narrative, choose the narrative.

---

## Creativity Belongs to Humans

Artificial Intelligence is powerful.

Creativity belongs to people.

The Game Master is always the author of the story.

The application should inspire rather than automate.

Whenever possible, offer ideas instead of decisions.

---

## AI Suggests, Humans Decide

AI-generated content is always a proposal.

Nothing becomes part of the campaign until accepted by the Game Master.

Every permanent change requires human approval.

Suggestions should encourage creativity, not replace it.

---

## Story Over Configuration

Users should spend time creating adventures.

Not configuring software.

Configuration should remain minimal and only appear when it creates real value.

Whenever possible:

- infer
- suggest
- simplify

instead of asking for more settings.

---

## Play Is More Important Than Preparation

Preparation exists for one reason:

To make live sessions better.

If a feature improves preparation but slows down gameplay, it should be reconsidered.

The application should disappear into the background once the session begins.

---

## Every Tap Has a Cost

Every interaction interrupts the Game Master.

Before introducing a new screen, dialog or form, ask:

> Is this interaction worth interrupting the story?

Reduce unnecessary confirmations.

Reduce unnecessary navigation.

Reduce unnecessary typing.

---

## Progressive Disclosure

Do not overwhelm users.

Show only what is relevant now.

Advanced functionality should appear naturally as users become more experienced.

The interface should reveal complexity gradually.

---

## Fast Beats Perfect

During a live session:

A good answer now is better than the perfect answer thirty seconds later.

The application should optimize for momentum.

Never interrupt storytelling for perfection.

---

## Context Is Everything

The application should understand where the Game Master is in the creative process.

Different contexts require different interfaces.

Examples:

Planning

↓

Creative workspace

Running Session

↓

Fast interactions

Session Summary

↓

Reflection and review

The application should adapt to the user's mindset.

---

## Physical Rewards Create Memories

Digital information disappears.

Physical rewards remain.

Printing is not an export feature.

It is part of the storytelling experience.

Receiving a sticker, badge or card should feel like a meaningful in-game reward.

---

## The World Should Feel Alive

Projects evolve over time.

Every completed adventure should leave visible traces.

Examples:

- characters grow
- locations change
- NPCs return
- Pokémon evolve
- world facts expand

The campaign should feel like a living world rather than disconnected adventures.

---

## Consistency Builds Trust

The application should behave predictably.

Identical actions should produce similar experiences.

Users should never wonder:

"What happens if I press this?"

Consistency reduces cognitive load.

---

## Simplicity Is a Feature

Simple experiences are harder to design than complex ones.

Whenever possible:

remove

instead of

add.

Every new feature increases complexity.

Complexity must always justify itself.

---

## Design for Emotion

Users rarely remember interfaces.

They remember moments.

Pokémon Stories should create moments like:

- catching a Pokémon
- earning a badge
- discovering a hidden place
- printing a new sticker
- finishing an adventure

Every feature should support memorable experiences.

---

## Respect the Game Master

The Game Master is never treated as a passive consumer.

They are a creator.

The application should:

- respect their decisions
- respect their creativity
- respect their pace
- respect their style

No feature should force a specific storytelling approach.

---

## Mobile Is the Primary Experience

The application is designed around phones.

Desktop layouts extend productivity.

They do not define the experience.

The mobile interface should never feel like a simplified desktop application.

It is the primary product.

---

## Offline Is a Valid State

Storytelling should continue even when technology fails.

Whenever practical:

- notes
- timelines
- rewards
- prepared adventures

should remain available.

Network failures should never stop the session.

---

## Technology Should Be Replaceable

No external technology should define the product.

Examples include:

- AI providers
- databases
- printing solutions
- cloud platforms

The product should outlive its implementation details.

---

# Product Decision Framework

Whenever designing a new feature, ask these questions:

1. Does it help tell better stories?

2. Does it respect the Game Master's creativity?

3. Does it improve the live session?

4. Does it reduce friction?

5. Does it strengthen the campaign world?

6. Does it create memorable moments?

7. Can it be simplified further?

If the answer to several questions is "no", the feature should be redesigned.

---

# Success Metrics

Pokémon Stories is successful when users say:

"I spent less time preparing."

"I felt more confident improvising."

"The children loved the rewards."

"I can't wait to run the next adventure."

Not when they say:

"It has many features."

---

# Final Principle

Every product decision should support one simple idea:

Technology should disappear.

The story should remain.
